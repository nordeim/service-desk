### F1 (HIGH — CI is red on main): the s17 og:image pin fails in the clean CI environment — ECONNREFUSED on the baked origin

`tests/e2e/visual-parity.spec.ts:2859` (the s17 og:image pin) fetches the og:image `content` attribute **as rendered** — an ABSOLUTE URL resolved from `NEXT_PUBLIC_SITE_URL` at render time (`http://localhost:3000/icon-512.png`; the fallback default when the var is unset, as in CI). The E2E webServer runs on **:3100**; nothing listens on :3000 in a clean environment → `ECONNREFUSED` → the suite fails 192/193.

**CI is red right now (badge-verified this session: "failing"):** the session-17 push (`806a510`) shipped this exact failure into the CI e2e job, and the operator-facing follow-up ("watch the CI run on GitHub") never happened — the red state sat unnoticed between sessions. The local 193/193 sign-off was true-but-lucky (see below).

**Why it passed in session 17:** the live paired re-verification production server was listening on :3000 during that session's E2E run — the pin's absolute-URL fetch silently hit the ambient server. A false-green by ambient infrastructure (the inverse of the s16 false-green polling-pin lesson: the environment satisfied the test, not the code under test).

**Fix:** resolve the URL's **pathname** against the page under test and GET that: `page.request.get(new URL(url, page.url()).pathname)` — `page.request` resolves relative paths against the context baseURL (:3100), so the asset GET goes through the E2E server regardless of what origin the metadata declares. The pin's full purpose is preserved (200 + `image/png` + PNG magic bytes — the response-layer doctrine), and it becomes deterministic in every environment (local clean, local dirty, CI — turning the red main badge green again). The og:image URL-pattern assertions (that it points at `/icon-512.png`) are untouched — they test the DECLARATION, which stays absolute per the OG spec.

### F2 (LOW-MED — asset truth): the favicon route `/icon.png` serves a 480×480 JPEG body under a false `image/png` content-type

`src/app/icon.png` (the Next file-convention favicon route) is actually a **JPEG** — the reference's logo fetched in session 2, saved with a `.png` name. The route serves it with `Content-Type: image/png` (Next derives type + `sizes` from the filename), and the rendered `<link rel="icon">` declares `type="image/png" sizes="480x480"` — **false on the type axis, exactly the "true-looking declaration over a false asset" defect class session 17 closed for og:image** (the s17 plan explicitly scoped the favicon out: "the favicon keeps serving the logo as before"; the s17 lesson 66 — "for every pinned meta, ask whether the asset behind it is what it claims" — now extends to the remaining head-facing asset).

**Measured both sides:** the reference's favicon is their supabase logo URL (a real PNG at their origin — the falsity is only in their og:image/manifest dimensions, already documented). Ours is the only side serving a mislabeled body. Browsers sniff and cope, but the declaration chain (link `type` attribute + response content-type + extension) is internally inconsistent on our side.

**Fix:** convert the 480×480 logo to a real PNG (identical pixels, honest container — the visual rendering is byte-equivalent; the file keeps the `src/app/icon.png` convention name so the route and the generated `<link>` stay unchanged). New E2E pin (the s17 og:image pattern extended to the favicon): GET `/icon.png` → 200 + `content-type: image/png` + **PNG magic bytes** (`89504e470d0a1a0a`) + the `<link rel="icon">` `type` attribute matching the served type.

### F5 (HIGH — CI root cause, found post-push): upload-artifact v4.4+ excludes hidden files by default — the standalone artifact NEVER carried `.next/` or `node_modules/.prisma`

**The evidence chain:** after the session-18 push (which fixed F1 and re-verified the suite green in a clean environment AND in a local artifact-round-trip simulation), the CI run STILL failed — at the "Run E2E suite" step, with the verify job green. Scraping the run history (the anonymous run-list aria-labels) then showed **every one of the 33 runs since the workflow's session-3 introduction failed** — CI has NEVER been green, while the local suite passed everywhere (clean env, CI-exact env, artifact round-trip). The step-level pattern (all steps green until the test step, exactly 1 error annotation) plus the never-worked history pointed at a structural, environment-only break.

**The root cause:** the workflow's artifact upload is `actions/upload-artifact@v4` with `path: .next/standalone` — and **upload-artifact v4.4+ EXCLUDES hidden files by default** (the `include-hidden-files` input defaults to `false`; documented in the action's README, fetched and verified this session). The standalone build is FULL of hidden paths: `.next/standalone/.next/` (the server chunks, every manifest, the static assets — the server cannot render a single page without it) and `.next/standalone/node_modules/.prisma` (the generated Prisma client — no database access without it). The restored artifact carried only `server.js` + `node_modules/` (sans `.prisma`) + `prisma/` + `public/` — a server that boots its health route but 500s every page and cannot touch the database. **The e2e job has been running against a gutted build since run #1.** (Why the local artifact simulation passed: `tar` does not discriminate against dot-directories — the simulation faithfully restored what the real upload step never included.)

**Fix (one input):** `include-hidden-files: true` on the upload step — shipped with a comment documenting the failure mode. The `@v4` tag resolves to ≥v4.6, where the input exists.

**Why 15+ sessions missed it:** the badge was never looked at between sessions (the session-17 sign-off said "watch the CI run on GitHub" and nobody did — the operator's transcripts don't mention it either), and every local gate (including this session's clean-environment and artifact-round-trip verifications) passes because the defect lives only in the upload step's default. ## 5. Process lessons (for the next agent)

1. **The verification infrastructure is itself a probe surface — and its STATUS is a claim to verify, not to trust.** CI is a badge on a repo page; nobody looked between sessions 17 and 18 while it sat red. When a test fetches an absolute URL, it tests whatever answers at that origin — pin the ORIGIN the suite controls (resolve through the E2E server) or the test is environment-hostage. The s16 polling-pin lesson ("run behavioral pins where only the surface under test fetches") extends from the page layer to the network layer.
3. **Clean-environment baselines catch what dirty ones hide.** This is the first session to run the E2E suite with no ambient :3000 server (a fresh clone forced it). Reproduce the target environment (CI's: no `.env`, no listeners) before claiming environment-independent results — the F1 failure was sitting in every clean clone of the repo.
