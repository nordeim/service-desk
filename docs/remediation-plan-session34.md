### P1 — the own-side audit at the new level: the cache-behavior surface (THE actionable gap)

The session_55 directive named the first candidate axis: the cache headers on the PAGE routes (never audited — the API routes carry the s30/s15 sets). The audit extended naturally across the whole response surface. Measured live on our production standalone :3000:

| Probe | Result |
|---|---|
| Authenticated `GET /dashboard` (with live cookie) | 200 + `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` — **SAFE** (Next's dynamic-render default; the earlier no-header reads were the cookie-less 307 bounce) |
| Static auth pages `/login`, `/signup`, `/forgotpassword` | `Cache-Control: s-maxage=31536000` — the framework prerender default; verified **PII-free** (0 user-data occurrences in the authenticated `/login` HTML) |
| sitemap/robots/icon | `public, max-age=0, must-revalidate` — safe |
| 404 page | `private, no-cache, no-store, max-age=0, must-revalidate` — safe |
| **Authenticated `GET /api/auth/me`** | **200, NO Cache-Control — the user's `{id, name, email}` in the body** |
| **Authenticated `GET /api/tickets` + `/api/stats`** | **200, NO Cache-Control — user-scoped ticket data** |
| The reference's entity API (`/entities/Core/Ticket`) | 200, `cf-cache-status: DYNAMIC`, no Cache-Control — **Authorization-header (JWT) authed: RFC 9111's mandatory shared-cache no-store covers them** |
| The reference's page routes | `cf-cache-status: DYNAMIC` on every route — their edge caches nothing |

**The judgment call.** Every authenticated JSON response under `/api/**` carries no caching directive. RFC 9111 §5.1 obliges a shared cache to reject storing responses to `Authorization`-header requests — the rule that saves the reference (their JWT rides the Authorization header) — but cookie sessions ride the `Cookie` header, which has NO equivalent protection. A shared intermediary (corporate proxy, ISP cache, or a CDN an operator fronts the standalone server with) MAY store our `/api/auth/me` response keyed by URL and serve user A's identity JSON to user B — the classic cross-user shared-cache leak. It is invisible in dev/E2E/smoke (no shared cache sits in the loop) exactly like the s15 timezone divergence was invisible at UTC — the class of bug that only fires in a proxied production deployment. The fix: `Cache-Control: no-store` on the whole API namespace — the same app-level, proxy-independent posture as the s30 HSTS decision (RFC 6797's inert-over-HTTP analogue: `no-store` is harmless locally, load-bearing behind any proxy). **Our superset — the reference's shape (no directive at all) would be strictly worse than either side's current posture.**

**The two design facts (measured on throwaway builds this session, the load-bearing facts for the fix):**

1. **A `headers()` rule's `Cache-Control` OVERRIDES the route handler's own `Cache-Control`.** A blanket `/api/:path*` no-store rule clobbered the s15 attachment route's `private, max-age=31536000, immutable` (verified live: the attachment download served `no-store`). The s15 year-long immutable private window — an E2E+smoke-pinned contract — would have silently died inside a "security" fix: the exact class of collateral damage the two-rule design exists to avoid.
2. **A more-specific rule listed AFTER the blanket rule WINS for the same key.** The two-rule design restores the s15 window on the attachment path while the blanket `no-store` holds everywhere else (verified live on both routes: the attachment download serves `private, max-age=31536000, immutable`; `/api/auth/me` serves `no-store`). **The rule ORDER in the `headers()` array is load-bearing — later-in-array wins.** Only ONE route in the codebase sets route-level `Cache-Control` (the attachment download — grep-verified), so the exception rule is exactly one.

### P2 — the auth-cookie lifetime under clock skew (verified NON-GAP — documented, no code)

The token `exp` (set from the SERVER clock at sign time, `SESSION_TTL_SECONDS` = 604800 s) is the AUTHORITATIVE validity gate — `verifySessionToken` checks it server-side on every request. The cookie `Max-Age` (applied by the CLIENT clock) only affects when the browser drops the cookie: a slow client clock keeps the cookie around past `exp`, but the server-side check returns null → the layout guard redirects to `/login`; a fast client clock drops the cookie early → the user re-authenticates. The two constants derive from the same `SESSION_TTL_SECONDS` (measured congruent to within seconds). **No skew scenario extends a session past the server-verified `exp` — the two clocks cannot disagree in a security-relevant way. Documented as a verified non-gap.**

## 2. The remediation (P1 — the API-namespace `no-store` contract)

### The design: two `headers()` rules in `next.config.ts`

1. **Rule 1 — the blanket:** `source: "/api/:path*"`, `Cache-Control: no-store`. Every JSON response in the API namespace — success AND error paths (the s32 envelopes, the s33 catch-all 404, the 401s) — tells shared caches never to store it. `no-store` (not `private`): the strongest single directive — `private` still permits browser-cache storage of the identity JSON on a shared device, and nothing in the app benefits from caching these responses (the sidebar re-fetches `/api/stats` every 5 s by contract).
2. **Rule 2 — the s15 exception (AFTER rule 1 — the order is load-bearing, later-in-array wins):** `source: "/api/tickets/:id/attachments/:attachmentId"`, `Cache-Control: private, max-age=31536000, immutable` — the byte-identical value the attachment route sets in code today. The route-level code stays untouched (the s15 seam, its comments, and its tests are all still true; the config now carries the final value — and the config-contract pin below owns it).
3. **The route-handler interplay is the design's OWN pinned contract:** the fact that the `headers()` rule overrides route-level headers is not documented anywhere in Next's docs and was measured empirically this session. The interplay pin (smoke + the config test) makes the precedence itself a contract — a future Next.js version changing the override order fails a pin instead of silently shipping a clobbered s15 window (or a silently-unprotected API).

### The pins (the s30 pattern extended — the config contract at the source of truth + the live surface)

1. **Unit pins (`tests/headers-config.test.ts`)** — extend the existing s30 config-contract file: the `/api/:path*` rule carries exactly `Cache-Control: no-store`; the attachment exception rule carries exactly the s15 value; the exception is listed AFTER the blanket rule in the array (the ORDER pin — the load-bearing fact); the universal `/(.*)` rule still carries its five s30 headers unchanged. A future edit that reorders the rules, drops the exception, or narrows the blanket source fails a pin.
2. **Smoke pins (the s34 block, ~6 pins):** on the throwaway server — (a) the authenticated `/api/auth/me` carries `no-store` (the identity-leak pin); (b) the authenticated `/api/tickets` carries `no-store`; (c) `/api/stats` carries `no-store`; (d) the catch-all 404 (`/api/banana`) carries `no-store` (the error-path pin); (e) `/api/health` carries `no-store`; (f) **THE interplay pin** — the attachment download (fixture: the s31 schema-pin ticket's attachment) still carries `private, max-age=31536000, immutable` + `Content-Disposition: inline` (the s15 contract survived the blanket rule; this is the pin that catches a Next.js precedence change). The rate-limiter arithmetic is untouched (no new login/forgot requests anywhere in the block — the fixture login reuses the existing top-of-script call).

### Non-goals (documented decisions, no code)

- **The static auth pages keep the framework's `s-maxage=31536000`:** public, PII-free content (verified — 0 user-data occurrences in the authenticated `/login` HTML); the reference's own shape (no directive at all) would permit heuristic caching — strictly worse; a shorter TTL is a host-policy decision, not a parity or security fix (the same reasoning as the s30 no-includeSubDomains decision).
- **The authenticated PAGE routes stay as-is:** they already carry `private, no-cache, no-store, max-age=0, must-revalidate` (Next's dynamic-render default — measured this session with a live cookie). No config needed; no pin added (the framework owns it, and pinning framework defaults invites drift fights with Next upgrades — the API namespace is OUR surface).
- **`Vary: Cookie` is NOT added:** with `no-store` on the whole namespace the Vary question is moot (nothing is stored, so nothing varies); adding it would imply storage is possible.
- **No change to the route-level `Cache-Control` in the attachment download's code:** the s15 seam and its comments stay byte-identical (the config exception carries the same value — belt and suspenders with identical values; the config-contract pin owns the final behavior).
- **The request-size cap (P3) is deferred to the next session** — the s24–s33 one-seam-per-session cadence (each strictness seam shipped with its own RED→GREEN + pins; piling two seams into one session muddies the bisection).
