## 1. Findings Inventory

### F1 (LOW-MED): the viewport meta is missing `viewport-fit=cover`

The reference ships `<meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover">` (live-measured this session on `/login`, `/submitticket`, `/dashboard`). Ours renders `width=device-width, initial-scale=1` — the `viewportFit` key is absent from the root layout's `Viewport` export.

**Why it matters:** `viewport-fit=cover` is what lets a page render edge-to-edge into the notch/home-indicator safe areas on iPhone X+-class devices. Without it, the browser letterboxes the viewport to the safe area — a visible geometry difference on every notched phone, and a bigger one for the PWA (our `/manifest.json` declares `display: "standalone"`; a standalone app without `viewport-fit=cover` insets its whole UI on notched devices, while the reference's installs render full-bleed). The reference's 11 safe-area padding rules (Tailwind CDN exhaust in their stylesheet) are generated-but-unused on their side — no element carries them — so no padding compensation exists on either side; the meta is the whole contract.

**Why 16 sessions missed it:** the s8 `<head>` sweep and the s11/s12 metadata work enumerated metas by NAME (description, og:*, twitter:*, apple-*) and pinned their PRESENCE — the viewport meta string was never value-diffed. The s8 lesson ("the head is bigger than the metas you grep for") extends: the values of the metas you already have are a probe surface too.

**Fix:** add `viewportFit: "cover"` to the `viewport` export in `src/app/layout.tsx`. Next renders it into the same meta tag (no new elements). `initial-scale=1` vs the reference's `1.0` is a string-spelling difference with identical computed behavior — not touched (parity is the computed value).

### F2 (LOW): the og:image declares 512×512 but serves the 480×480 JPEG at `/icon.png`

Our root `openGraph.images` declares `{ url: "/icon.png", width: 512, height: 512, alt: "ServiceDesk" }`. The asset actually served at `/icon.png` (via the `src/app/icon.png` file convention — the reference's logo, fetched in session 2) is a **480×480 JPEG** served with `Content-Type: image/png` (verified live: GET returns 200, 27043 bytes, `file` reads JPEG 480×480; PNG magic absent). The declaration is false on both axes — the dimensions AND the type.

**Measured both sides:** the reference declares `og:image:width=1200, og:image:height=630` against THEIR og:image URL — which serves the SAME 480×480 JPEG (fetched and verified this session). Their 1200×630 declaration is a base44 platform default applied to the app logo — a platform defect, the exact defect class the s11 manifest work documented ("the reference declares two sizes against one 480×480 JPEG") and refused to mirror.

**Fix (the s11 precedent — our side tells the truth):** point `openGraph.images` at `/icon-512.png` — the REAL 512×512 PNG that already exists in `public/` for the PWA manifest (generated in s11 from the same logo; the s11 manifest pin already verifies it serves 200 as `image/png`). The declared 512×512 becomes true, the MIME becomes true, and no new asset is needed. The s12 mechanism pin's URL regex (`/\/icon\.png/`) updates to `/icon-512\.png/` alongside (its purpose — the og set survives the openGraph replace — is unchanged).

**Why it matters:** social-card crawlers (Facebook/LinkedIn/WhatsApp) read `og:image` + the declared dimensions to size the preview; a false declaration risks cropped or mis-rendered cards. LOW severity (no in-app UI), but it is a factual correctness issue on the response layer — the s14 doctrine applied to metadata.

1. **Meta VALUES are a probe surface, not just meta PRESENCE.** Sixteen sessions of head work pinned which metas EXIST; the viewport string and the og:image's pointed-at asset were never value-diffed. Two of this session's three findings were "a true-looking declaration over a false asset."
3. **Shortlists close fast when the bundle is the instrument.** The stat-card hover-path and heartbeat questions (open since session 21) each resolved in one bundle read — no app-level `whileHover` exists; the heartbeat drives only the admin table. Read the bundle FIRST when a question is about behavior the bundle encodes.
