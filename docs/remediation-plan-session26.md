### P1 (the session's actionable finding → the fix): the list API's `search` param — the LAST unaudited param family on the route, carrying a genuine parity bug: Prisma's SQLite `contains` compiles to a bare `LIKE` with NO `ESCAPE` clause, so `%` and `_` in the user's search act as wildcards — a literal `%` silently renders the unfiltered feed

**The own-side audit (the s23/s25 doctrine — audit OUR advertised contract with the same curl-the-API rigor pointed at theirs) found the one param family s24/s25 did not cover:**

- **The live measurements (production standalone :3000, the demo user, `scope=all`):** `?search=%` → **200 with all 11 rows** (the unfiltered feed — the wildcard `%` matches everything); `?search=_` → **11 rows** (the single-char wildcard); `?search=%signature%` → 1 row (the wildcards absorbed — identical to `?search=signature`); `?search=zzzz-nomatch` → 0 (the normal path works); `?search=<5000 chars>` → 200 (no length cap — an unbounded `LIKE` pattern). The generated SQL confirmed at the Prisma layer: `contains('%')` → parameter `"%%%"`, and `contains('\\%')` → `"%\%%"` — **the backslash is a literal character because Prisma emits no `ESCAPE` clause** (measured via query logging — 0 rows for `\%`, i.e. escaping inside the value cannot work).
- **The reference's measured semantics (pinned at the bundle, `index-DhFaB31Z.js`):** their mytickets search filters client-side — `title.toLowerCase().includes(r.toLowerCase()) || description.toLowerCase().includes(r.toLowerCase())` — **literal case-insensitive substring match**; `%` and `_` have no wildcard meaning on their side. **This is a genuine parity bug on a user-visible surface:** a user typing `%` (or any term containing it — "50%", "100% CPU", a file name with `_`) into our search box gets wrong results — in the pure-wildcard case, the entire unfiltered feed presented as if it matched. The lesson-79 class exactly: a silently-transformed param is a lie the caller pays for.
- **The callers audited:** the UI sends `search.trim()` when non-empty (the mytickets page); the smoke script sends `?search=Smoke` (a plain word); the E2E suite sends no `search=` directly (grep-verified) and the UI-driven specs type plain words. **No legitimate caller sends a wildcard-bearing or over-length search — but the user typing one into the box IS the legitimate case this fix protects.**

**The fix (P1 below, TDD):** the literal-search contract at the seam — `parseListSearch` in `validation.ts` (trim + a constants-borne `SEARCH_MAX_LENGTH = 200` cap + a 400 with the s24/s25 message style), the route's search predicate rebuilt as a raw-SQL **id-subquery using `instr(lower(col), lower(?))`** (literal case-insensitive substring — byte-equivalent to the reference's semantics; `instr` cannot be confused by wildcards and needs no ESCAPE clause), the ids feeding `where.id = { in: […] }` so the where-builder/orderBy/pagination/includes and the response shape stay byte-identical; the UI search Input mirrors the cap with `maxLength={200}` (an invisible-superset guard — the reference's own input has no maxLength; ours prevents the surprise 400 without any visual difference).

**Why the id-subquery and not a raw full query:** the two-step keeps the pinned route contract untouched (the `include` shape, the sort-in-JS priority branch, the pagination wiring all stay Prisma-native); the raw step touches only the one predicate Prisma cannot express (literal contains). The subquery is unbounded by design — it returns ids, not rows (the corpus is the ticket table; the reference fetches the FULL ticket list client-side for the same feature — our server-side id scan is strictly cheaper). The known limit, documented: SQLite `lower()` is ASCII-only (as is `LIKE`'s case-insensitivity — the shipped contract; no regression).
